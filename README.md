# ER Intake Triage — Structured-Output LLM Pipeline

**Turning messy patient transcripts into validated, clinically actionable triage decisions using LLM structured outputs.**

> Companion code for the presentation *Beyond the Chatbot — Building LLMs into Business Systems*
> by Matt Hergott ([Mirabella AI](https://mirabellaai.com)) · Denver Data Dialogues · March 10, 2026

---

## The Problem

Emergency-room intake conversations are messy. Patients say "um," approximate dates, use layperson language, and bury critical clinical signals inside rambling narratives. A chatbot can clean this up into readable prose — but prose is an opaque blob. You can't query it, route on it, or score it. It doesn't plug into a hospital EHR, a bed-management dashboard, or a pre-authorization system.

**Structured outputs change everything.** By defining a typed Pydantic schema and constraining the LLM to return validated JSON that conforms to it, the same model output becomes queryable, scoreable, and directly consumable by downstream business systems — no post-processing regex, no fragile parsing, no manual review.

## What This Program Does

This pipeline submits a full corpus of simulated ER intake transcripts to a Groq-hosted LLM, constrains the response to a deeply nested Pydantic schema, validates the result, and renders three output artifacts:

1. **A presentation-quality plain-text report** with ASCII severity/risk bars and nested 4-level analysis
2. **A self-contained dark-themed HTML report** with color-coded risk visualization
3. **A business integration showcase** demonstrating 8 real-world system integrations using live data from the triage result

One command. Messy transcripts in, validated clinical triage decision out.

## The Four-Layer Schema

The structured output enforces a bottom-up clinical reasoning chain — each layer narrows the analysis toward a single actionable decision:

```
Layer 1: SymptomRead        Patient language → canonical clinical terms + severity (-5 to +5)
    ↓
Layer 2: SymptomCluster     Pattern recognition across related symptoms, flagging acute conditions
    ↓
Layer 3: RiskCalc           Worst-case diagnosis + how fast the window is closing (0.0–1.0)
    ↓
Layer 4: Triage             A single judgment: surgery | ICU | observation | discharge
```

**The key insight:** adding a single `urgency_score` field — where the model evaluates *what was said*, *how it was said*, and *what was not said* — represents a quantum leap beyond traditional NLP. Context, nuance, and clinical implication are unlocked by the schema, not by the model alone.

## Architecture

```
settings.py          → Runtime configuration (model selection, data file, paths)
data_structures.py   → Pydantic schema (the structured-output contract)
prompts.py           → Sandwich-pattern prompt construction
groq_api_client.py   → Async API client with smart retries
main.py              → Orchestration, validation, text report rendering
html_report.py       → Self-contained HTML5+CSS report generator
business_integration.py → 8 integration use-case showcase generator
```

### Sandwich Prompting

The prompt wraps the full transcript corpus between opening task instructions and closing quality-gate requirements. This prevents the model from short-circuiting with a quick summary and forces full-corpus analysis across all transcripts.

### Smart Retry Loop

Failed structured-output attempts aren't discarded — each error and raw output is appended back into the next prompt, giving the model self-correction context. Up to 6 attempts with accumulated feedback.

## Simulated Data

> **All patient data in this repository is simulated.** The intake transcripts were generated by an LLM for the sole purpose of demonstrating this structured-output pipeline. No real patient information is present anywhere in this project.

The included dataset (`er_intake_mitral_emergency.txt`) contains **16 simulated intake transcripts** for a fictitious 57-year-old male construction foreman spanning January 12 – March 4, 2026. The transcripts deliberately include:

- **Layperson language** — "puffy ankles," "can't catch my breath," "heart doing flip-flops"
- **Confounding presentations** — seasonal allergies, deconditioning, work stress, back strain
- **Progressive clinical deterioration** — fatigue → dyspnea → acute pulmonary edema with pink frothy sputum
- **A hidden diagnosis** — acute severe mitral regurgitation with chordae tendineae rupture, masked by benign-seeming complaints

The correct triage routing is **SURGERY** (emergency mitral valve repair).

## Quick Start

### Prerequisites

- Python 3.13+
- A [Groq API key](https://console.groq.com/)
- Dependencies: `openai`, `pydantic`, `python-dotenv`, `aiohttp`

### Setup

```bash
# Create and activate a virtual environment
python3 -m venv .venv
source .venv/bin/activate

# Install dependencies
pip install openai pydantic python-dotenv aiohttp

# Set your Groq API key
echo "GROQ_API_KEY=your-key-here" > src/.env
```

### Run

```bash
python src/main.py
```

### Configuration

Edit `src/settings.py` to change the model or input dataset:

```python
MODEL = "openai/gpt-oss-120b"                        # or "openai/gpt-oss-20b"
SIMULATED_DATA_FILENAME = "er_intake_mitral_emergency.txt"
```

## The Presentation

📄 **[Data_Dialogues_Beyond_the_Chatbot_10Mar2026.pdf](Data_Dialogues_Beyond_the_Chatbot_10Mar2026.pdf)** — Full slide deck from the Denver Data Dialogues talk.

The presentation traces an arc from **tools** (what coding agents exist today) → **technique** (structured outputs and Pydantic schemas) → **architecture** (chain-of-thought orchestration across layers) → **philosophy** (the prompt as the product). Key themes:

- **From text to structure** — Why a chatbot's prose output is an opaque blob, and how a typed schema makes it actionable
- **Constrained decoding vs. code enforcement** — Two paths to guaranteeing valid structured output
- **The four-layer chain** — How layered schemas produce more reliable reasoning than single-shot prompts
- **Architecture over model size** — Structured steps let even smaller models produce analysis beyond their native capability
- **Program recipes** — If coding assistants are kitchens, prompts are recipes. The structured specification is what counts.

## Technical Details

| Component | Detail |
|-----------|--------|
| Python | 3.13+ |
| LLM provider | [Groq](https://groq.com/) (OpenAI-compatible API) |
| Models | `openai/gpt-oss-20b`, `openai/gpt-oss-120b` |
| Schema enforcement | Pydantic v2 via `responses.parse` structured output mode |
| Async transport | `aiohttp` via `DefaultAioHttpClient` |
| Retry strategy | Up to 6 attempts with error context fed back into the prompt |
| Output tokens | Capped at 12,000 per request |
| Request timeout | 180 seconds |
